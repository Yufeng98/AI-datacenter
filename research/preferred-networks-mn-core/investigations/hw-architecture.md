# Preferred Networks MN-Core Hardware Architecture Investigation

*as_of: 2026-08-08*
*chip: preferred-networks-mn-core*
*device_class: Compiler-Scheduled SIMD Accelerator (Japan)*

---

## Overview

**Preferred Networks, Inc. (PFN)**, Tokyo, designs the **MN-Core** series of deep-learning and HPC accelerators, co-developed with **Kobe University** (Prof. Junichiro Makino's group; Makino is also PFN's CTO of Computer Architecture). Development began in 2016.

Three generations exist publicly:

1. **MN-Core** (gen 1, TSMC 12 nm, 4-die MCM) — deployed in production; powered the **MN-3** supercomputer (three Green500 #1 finishes) and the commercial **Matlantis** materials-simulation service. Superseded.
2. **MN-Core 2** (gen 2, TSMC N7, single 550 mm² die) — the current shipping part. Sold as complete Japanese-market systems and offered as a cloud service.
3. **MN-Core L1100 / L1400** (the "MN-Core L1000" architecture) — **announced, pre-silicon, mockup only, 2027 target**. Nothing about this part should be described as shipping.

Internal die codenames: gen-1 dies are marked **`GPFN-2G01`** on PFN's own package photograph; MN-Core 2 is **GPFN3** internally — the SDK's management tool is `gpfn3-smi`, the emulator `gpfn3_package_main`, the assembler `assemble3`, and the MLSDK docs state verbatim that these target "MN-Core 2 (also known as GPFN3)".

The architecture's defining property is what the hardware **omits**. This is what makes it interesting for a software-stack survey.

---

## 1. Design Philosophy — What Is Deliberately Absent

PFN's own framing, repeated verbatim across the whitepaper, the business page and every recent press release: functions "such as network control circuits, cache controllers and command schedulers, are incorporated in the compiler software rather than the hardware."

The Software Developer Manual is blunter:

> "There are no hardware-managed caches in MNCore 2, and all the intra-board data transfers are explicitly managed by using machine code instructions. **Instructions are sent to the board in a single stream and there are no mechanisms to manage the control flow of the execution.**" — SDM §1.1

And the whitepaper:

> "Processing Element (PE) on the accelerator does not have its own program counter or instruction decoder. All PEs operate in perfect synchronization, receiving instruction sequences generated by the host CPU directly from the host."

Note the precise consequence: instruction issue is not merely "moved into the compiler" — the **host CPU is part of the execution model at run time**, streaming a single instruction stream over PCIe to a device with no fetch unit of its own.

PFN quantifies the payoff: **7.4 % of MN-Core 2's transistors are in arithmetic units**, versus PFN's own measurements of 1.7 % ("GPU N"), 2.4 % ("Accelerator P") and 1.3 % / 0.8 % (two CPUs). *(Vendor claim; PFN's own research; comparators anonymized.)*

Makino's Hot Chips 36 framing places the machine in the lineage of "large-scale SIMD machines like TMC CM-2 and MasPar MP-2", with the "network architecture simplified and optimized for deep learning". He also describes it as a **register-memory architecture, not load-store** — local memories can be named directly as instruction operands.

| Hardware block found in a conventional accelerator | MN-Core 2 equivalent |
|---|---|
| Hardware data cache (any tier) | **Absent.** Scratchpad at every level; compiler places every byte |
| Cache controller / replacement policy | Compiler: Location Planner + Scheduler spill/refill/`Forget` |
| Instruction fetch, program counter, decoder (per PE) | **Absent.** Host streams the instruction stream |
| Hardware instruction scheduler / OoO / scoreboard | **Absent.** VLIW; compiler-scheduled |
| Hazard interlocks | **Absent.** Programmer/compiler must space dependent instructions |
| Branch unit / control flow | **Absent.** Mask-register predication only |
| NoC router / mesh | Broadcast/reduction **tree** with fixed transfer modes |
| Chip-to-chip fabric | **Absent on MN-Core 2** (gen 1 had MN-Core DirectConnect) |

## 2. Compute Engine — MN-Core 2

### 2.1 Headline specifications

All confirmed against the MN-Core 2 White Paper (2023-11-12).

| Parameter | Value |
|---|---|
| Manufacturing process | TSMC **N7** |
| Die area | **550 mm²** (single die) |
| Transistors | **22 B** |
| Operating frequency | **750 MHz** |
| PEs | **4096** |
| MAUs (matrix units) | **1024** *(derived: 4096 PEs ÷ 4 PEs per MAB)* |
| Peak FP64 | **12 TFLOPS** |
| Peak FP32 | **49 TFLOPS** |
| Peak "TF32" (PFN pseudo-single, block-FP) | **98 TFLOPS** |
| Peak "TF16" (PFN half, block-FP) | **393 TFLOPS** |
| Power | **330 W (design value)** |
| Energy efficiency | 37.24 (FP64) / 148.9 (FP32) / 297.9 (pseudo-single) / **1192 (half) GFLOPS/W** |

> ⚠️ **The widely quoted 1192 GFLOPS/W is the half-precision figure only.** FP64 efficiency is 37.24 GFLOPS/W. Quoting 1192 without the precision qualifier is the single most common error about this chip.

### 2.2 The MAB / MAU, and where the peaks come from

Each **MAB (Matrix Arithmetic Block)** = **4 PEs + 1 MAU (Matrix Arithmetic Unit)**. The MAU carries a **double-buffered matrix register** (two "sides", so one side can be multiplied against while the other is written).

Per-cycle capability of one MAU (SDM §1.4):

**Matrix–vector multiply-add** `y = A·b + c`, for an *m*×*n* matrix A:

| Precision | m | n | Operand format | Accumulator/result |
|---|---|---|---|---|
| Double | 2 | 4 | A, b block-FP double | c, y normal double |
| Single | 8 | 4 | A, b block-FP single | c, y normal single |
| Pseudo-single | 8 | 8 | block-FP, shorter effective mantissa than single; **exists only in block-FP form** | c, y normal single |
| Half | 16 | 16 | A, b block-FP half | c, y normal **single** |

**Vector multiply-add** `y = a*b + c`, element-wise: double m=4 (with a caveat — only elements 0/1 *or* 2/3 of the product can be enabled per issue, so a full 4-element FMA takes two issues), single m=8, half m=16 (a, b half; c, y single).

Peak FLOPS reconcile exactly *(derived)*:

| Precision | Arithmetic | Result |
|---|---|---|
| FP64 | 2 × 4 × 2 × 1024 × 750 MHz | 12.29 TFLOPS |
| FP32 | 8 × 4 × 2 × 1024 × 750 MHz | 49.2 TFLOPS |
| Pseudo-single | 8 × 8 × 2 × 1024 × 750 MHz | 98.3 TFLOPS |
| Half | 16 × 16 × 2 × 1024 × 750 MHz | 393.2 TFLOPS |

> **Therefore the whitepaper's "TF32" is PFN's own pseudo-single block-FP format and its "TF16" is block-FP half — neither is NVIDIA TF32 nor IEEE binary16.** Do not equate them in a comparison table without the qualifier.

Each **PE** additionally has an **ALU** (integer and general ops including special ops such as ReLU) plus mask registers. Reduction units (floating-point add and other reductions) also exist in the PE→L1BM→L2BM uplink paths, but PFN explicitly states these are **not counted in peak FLOPS**.

**Integer matrix datapath (INT8/INT4): not disclosed.** The SDM documents only FP/BFP matrix modes; the compiler exposes integer dtypes but only for ALU-class work. Absence of an integer MAU mode is not explicitly confirmed by PFN.

### 2.3 Number formats — non-IEEE, and this matters

MN-Core 2 floating-point is **not IEEE-754-compatible** (SDM §1.3; MLSDK Hardware Specification §7.3):

| Precision | Sign | Exponent | Mantissa | Notes |
|---|---|---|---|---|
| Half (HW, 16-bit) | 1 | **6** | **9** | **Not IEEE binary16** (1-5-10) |
| Single (SW, 32-bit) | 1 | 8 | 23 | IEEE-like field widths |
| Double (LW, 64-bit) | 1 | 11 | 52 | IEEE-like field widths |

- **No denormals and no NaNs at all.** Exponent all-zero ⇒ ±0 regardless of mantissa; exponent all-ones ⇒ ±∞ regardless of mantissa.
- Max positive half = 4.29e+09; min positive normal half = 9.31e-10 — a much wider exponent range than binary16 with less mantissa.
- **Block floating point (BFP)**: matrix–vector operands must be BFP-converted first; BFP uses the same field widths but **no hidden bit**. "In MN-Core, block-floating-point arithmetic was used only for half precision, but in MN-Core 2, **it is used for all precisions**" — including FP64 matrix ops.
- Assembly is **untyped**: an MAU float result can be fed to the integer ALU with no check.
- Integer dtypes exposed by the compiler: Int8, Byte, Short/UShort, Int/UInt, Long/ULong, plus Half/Single/LongBool.

## 3. On-chip Memory — 100 % Software-Managed, No Cache at Any Level

The chip is a **tree**: Top Level → 4 Groups → 8 L2Bs → 64 L1Bs → 1024 MABs → 4096 PEs.

Capacities are documented in **LW** (long word = 64 bits = 8 bytes):

| Level | Unit | Capacity (as documented) | Per-chip total *(derived)* | Ports / notes |
|---|---|---|---|---|
| PE | **GRF0 / GRF1** | 256 LW each = 2 KiB each | 16 MiB | 1R1W, 2 LW/cycle each |
| PE | **LM0 / LM1** (Local Memory) | 2 Ki LW each = 16 KiB each | **128 MiB** | 1RW, 2 LW/cycle each |
| PE | **T-register** | 8 LW = 64 B | 256 KiB | 1R1W, 2 LW/cycle |
| L1B | **L1BM** | 8 Ki LW = 64 KiB | 4 MiB | 64 L1Bs |
| L2B | **L2BM** | 32 Ki LW = 256 KiB | 2 MiB | 8 L2Bs |
| Group | **PDM** (PIU Data Memory) | 4 MiB (512 Ki LW) per group | 16 MiB | SRAM; PIU = PCIe Interface Unit |
| Group | **DRAM** | 4 GiB per group | 16 GiB | Off-chip main memory |

**Aggregate on-chip SRAM ≈ 166 MiB** — this is *our arithmetic from the per-level figures*; **PFN does not publish an aggregate figure**, so treat 166 MiB as derived, not as a vendor spec.

Structural facts that shape the software stack:

- **Only Group 0's PDM is physically connected to the host over PCIe.** *All* host↔device I/O funnels through that one 4 MiB PDM.
- The compiler's `Location` abstraction can only place tensors in **DRAM or LM0/LM1**: "Regarding GRF0/GRF1 and L1BM/L2BM, these are not assigned as Locations." Those tiers are scratchpad/transfer buffers managed inside operator implementations.
- PFN's rationale for LM: it "combines the advantages of high-speed SRAM access from the PE with substantial total capacity, enabling minimal DRAM access and effectively improving the overall B/F ratio. However, it lacks advanced memory management features like cache memory, and **all data transfers must be explicitly specified**."
- Address units in assembly: DRAM `$d`, PDM `$p`, L2BM `$lc`, L1BM `$lb` are LW-addressed; LM0 `$m`, LM1 `$n`, GRF0 `$r`, GRF1 `$s` are SW (32-bit) addressed. Storage is **big-endian**; results shorter than 2 LW are MSB-aligned.

**Derived aggregate LM bandwidth** *(arithmetic implication of documented port widths, not a PFN figure)*: 4096 PEs × 2 LW/cycle × 8 B × 750 MHz ≈ **49 TB/s per LM bank**, ≈ **98 TB/s across LM0+LM1**.

**L1BM and L2BM SRAM bandwidth: not disclosed** as such — only per-instruction LW/cycle throughputs are documented, and only for MV instructions.

## 4. On-chip Interconnect — a Broadcast/Reduce Tree, Not a Mesh or Crossbar

There is no NoC in the usual sense. Each tree level is a **broadcast/reduction network** with a fixed repertoire of transfer modes:

- **L1B**: 16 MABs + one L1BM. Modes between L1BM and MABs/PEs: broadcast, individual transfer, **reduction**, distribute/collect. "These data transfers are controlled by PE instructions."
- **L2B**: 8 L1Bs + one L2BM, same repertoire between L2BM and L1Bs.
- **Top level / Group**: data engines in each Group move data among PDM, DRAM and L2BM, within and across groups.
- **Transfer directions are symmetric by design**: for every downward mode (e.g. distribute) there is a matching upward mode (collect) that reassembles the identical layout — the SDM calls this out explicitly as a layout-consistency property.

PFN's argument for why a tree beats a cache hierarchy: "This variety of transfer modes enables highly efficient execution of fine-grained parallel tasks, which is difficult with multiprocessors using hierarchical caches." Makino: broadcast and reduction "are the two most important communication patterns for PEs used for tensor operations in deep learning. Compared to shared cache, energy consumption becomes much smaller."

Documented MV-instruction throughputs (SDM §3.5.8, sampled) give the actual tree bandwidths:

| Path | Throughput | At 750 MHz *(derived)* |
|---|---|---|
| DRAM ↔ L2BM parallel transfer | 16 LW/cycle per group | 96 GB/s per group |
| Inter-group broadcast / reduce | 8 LW/cycle | 48 GB/s |
| L2BM-side collect / distribute | up to 32 LW/cycle | up to 192 GB/s |
| PDM ↔ L2BM individual | 8 LW/cycle PDM side, 1 LW/cycle L2BM side | — |
| PDM ↔ DRAM | 8 LW/cycle PDM side, 2 LW/cycle DRAM side | — |

## 5. Data Path / Execution Model — Instruction Supply *Is* the Architecture

- **Two instruction classes**: **MV instructions** (data movement among the "upper memories": PDM, DRAM, L2BM, across groups) and **PE instructions** (control everything at L2B and below — despite the name).
- **PE instructions are VLIW** and "control the entire L2Bs and below in **4 cycles**. This 4-cycle unit is called a **step**." The SDM footnote is the key architectural disclosure: *"This is because 1 cycle per instruction would saturate the PCIe bandwidth between the host and the board."* **The instruction issue rate is literally set by the host link.**
- **Two packing modes**: **auto-stride** (instruction-stream unit = 3 PE instructions + 1 MV instruction; addresses auto-increment each cycle within a step) and **flat** (2 PE + 1 MV; GRF0/GRF1/LM0/LM1 addresses specified per cycle — more flexible, more instruction bandwidth). Auto-stride is a strict subset of flat. Real hardware requires packed streams; the emulator does not.
- **No hazard interlocks.** "Instruction execution is pipelined, and the results cannot be used immediately after the instruction is issued. **It is the programmer's responsibility** to leave cycles until the value written to one of the memories can be read." (SDM §3.6.3, "Avoiding Hazards".)
- **No branches.** PFN: "Entirely composed of SIMD with no conditional branch." Predication is via **mask registers** written by ALU result flags.
- **MV instructions execute asynchronously**; synchronization is an explicit **`wait`** field carried in every PE instruction (fixed-width, so `wait` is always present with a "don't wait" encoding).
- **Forwarding paths are architecturally visible operands**: `mauf` (MAU result forward), `aluf` (ALU result forward), `lbf` (L1BM→PE forward), `mreadf` (transposed matrix-register read forward), `nowrite` (dummy output). MN-Core 2 added "direct feedback paths from MAU/IALU" relative to gen 1.
- **Determinism is the marketed consequence** *(vendor claim)*: "Without cache interference or speculative behavior, execution is fully deterministic — the performance you measure in simulation is the performance you get on hardware."

**Instruction-stream bandwidth from host in GB/s, and any instruction buffering/staging capacity on the board: not disclosed.**

## 8. Scale-up Interconnect — There Is None on MN-Core 2

This is an important negative result. **MN-Core 2 has no chip-to-chip fabric, no NVLink/Infinity-Fabric analogue, and no device-side collectives.**

- Multi-board and multi-node execution in the SDK is done **through the host**: PFN's own pipeline-parallel Llama example runs `mpiexec -n <stages>` with `torch.distributed` on the **`gloo`** backend and host-side `dist.send`/`dist.recv`.
- **Gen 1 *did* have a proprietary fabric**: **MN-Core DirectConnect**, "an interconnect technology developed specifically for MN-Core", with **MN-Core DirectConnect Switches**; 32 MN-Core Servers + 2 switches = one "Zone". No equivalent is documented for MN-Core 2.
- PFN has never explicitly stated whether DirectConnect was dropped or simply not used in MN-Server 2. **Treat as not disclosed, not as confirmed removal.**

## 9. Scale-out Interconnect

Standard host networking only. **MN-Server 2 V1**: 2 × NVIDIA ConnectX-6 100 GbE dual-port plus onboard 2 × Intel X710 10 GbE. No RDMA path from the accelerator itself; no collective-communication offload.

## 11. Measured / Vendor-Reported Performance

From Hot Chips 36 (PFN's own measurements, MN-Core 2 vs A100) — *vendor claim, dated 2024-08-27*:

| Workload | MN-Core 2 | A100 |
|---|---|---|
| GCN (PFN internal) | 5.41 TF (FP32) | 3.17 TF |
| ResNet-50 training | 77 TF (FP16) | 33.2 TF (BF16) |
| ResNet-50 inference | 154 TF (FP16) | 33.7 TF (BF16) |
| HIMENO benchmark | **9.03 TF (FP64)** | 0.634 TF |
| OpenFDTD | 0.655 TF (FP32) | 0.488 TF |

The HIMENO result (14× A100) is the striking one; PFN attributes it to "much larger on-chip memory" plus temporal blocking. 9.03 TF FP64 out of a 12 TF peak is ~75 % of peak on a memory-bound stencil — a direct consequence of the 128 MiB software-managed LM.

**LLM inference on MN-Core 2** (SDK v0.6, PLaMo-3-NICT-2B-base): **5,100 tok/s prefill (512 tok), 11.8 tok/s decode** *(vendor claim)*. PFN also ran **PLaMo 3.0 Prime β for MN-Core (8B)** on liquid-cooled MN-Core 2 servers in the Interop Tokyo 2026 ShowNet (June 2026).

**No MLPerf or other third-party-audited results exist for MN-Core 2.** The only independently verified performance datum in the whole MN-Core line is the gen-1 Green500 ranking.

## 13. MN-Core L Series — PRE-SILICON, 2027 TARGET

**Status as of 2026-08: a mockup only.** One was exhibited at SC25 (Nov 2025) and photographed in the June 2026 Toyota press release ("MN-Core L1400, a model in the MN-Core L series (**mockup**)"). PFN's roadmap graphic marks L1000 as 開発中 (*in development*).

**Naming.** "MN-Core L1000" is the **architecture/family**; the announced SKUs (2026-06-01) are **MN-Core L1100** (low-power) and **MN-Core L1400** (high-performance), both targeted at **2027**. The original 2024-11-15 announcement targeted 2026 — a **one-year schedule slip**.

**Memory technology — the whole point of the part.** "PFN's proprietary **logic and DRAM are vertically stacked, with many electrodes arranged across the surface**, enabling even higher bandwidth and lower power consumption." PFN contrasts it against GPU+DRAM, GPU+HBM, and SRAM-based inference chips (which it says lack capacity). It is **DRAM-on-logic 3D stacking**, described by PFN as "relatively low-cost, high-capacity DRAM" — **not commodity DIMM DRAM, and not HBM**.

**Claims (all vendor, all unverifiable pre-silicon):**
- "**50 times higher memory bandwidth than MN-Core 2**" (2026-06-01). *Arithmetic implication, derived from a vendor claim and not a published spec*: 50 × 512 GB/s ≈ 25.6 TB/s.
- "For widely used LLMs with 70 billion parameters, a **single MN-Core L1400 card** is designed to provide the memory bandwidth and memory capacity required for inference."
- The earlier and *different-in-kind* 2024 claim: "up to a **ten-fold increase in computing speed** compared with conventional processors such as GPUs."

**Design-win status.** The Toyota Frontier Research Center engagement (2026-06-01) is **joint research on software** for an unreleased chip: PFN supplies software, FRC researches robot inference acceleration, and real-world robot tests happen only "following 2027 shipments." **This is not a deployment and not a customer.**

**Not disclosed for L1100/L1400:** process node, foundry, die size, DRAM stack vendor/technology, layer count, memory capacity, absolute memory bandwidth, peak FLOPS, supported dtypes, TDP, form factor, price, interconnect, or any differentiation beyond the labels "low-power" and "high-performance".

- **2026-04 onward**: upgraded and moved into IIJ's Shiroi DCC modular liquid-cooled data center (**AImod**; design pPUE 1.1 free-cooling / 1.2 annual, WUE 0, 400 V three-phase four-wire, 7:3 water:air). **Board counts for the Shiroi deployment not disclosed.**
- **PFCP cloud**: multi-tenant Kubernetes over MN-Server 2 V1 nodes (8 boards each), reserved (monthly fixed) or shared (pay-as-you-go). **Fleet size not disclosed; pricing not published.**
- **Production applications on gen-1 MN-Core**: Matlantis (materials MLIP simulation, sold commercially to ENEOS as a cloud service since Aug 2023, ~3–5× vs GPU); PFN 3D Scan (~10×); Kachaka home-robot NAS (~7×). MN-Core 2 has been used in Matlantis **experimentally** via PFCP.

## 17. Explicitly Not Disclosed

- Aggregate on-chip SRAM capacity as a single published figure (per-level capacities are documented; ~166 MiB is our arithmetic)
- GDDR6 bus width, device count, per-pin data rate; PFN's own slides are inconsistent between "GDDR6" and "GDDR6X"
- Board mechanical form factor and card dimensions
- Per-board idle power, measured TDP (as opposed to the 330 W design value), thermal limits
- L1BM/L2BM SRAM bandwidth figures (only per-MV-instruction LW/cycle throughputs are documented)
- Instruction-stream bandwidth from host in GB/s; instruction buffer/staging capacity on the board
- Whether any integer matrix datapath (INT8/INT4) exists in the MAU
- Yield, unit volume shipped, total boards in PFN/PFCP fleets beyond the 240 + 16 NEDO testbed
- Die photo / floorplan and per-block area breakdown
- Sparsity support, weight compression, on-chip decompression (none documented; absence not explicitly confirmed)
- Virtualization / MIG-style partitioning (the runtime takes an exclusive device lock, but PFN does not state whether partitioning is possible)
- RAS: ECC on DRAM or SRAM, error reporting, secure boot on the accelerator itself
- Everything about MN-Core L1100 / L1400 silicon, and everything about L2000
- Whether the post-MN-Core-2 training part is Samsung SF2 or Rapidus-manufactured
- Whether MN-Core DirectConnect was dropped for gen 2 or merely unused
