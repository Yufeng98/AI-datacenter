## Overview

AMD's operator library stack for deep learning consists of three cooperating layers: **MIOpen** (DNN primitives, AMD's cuDNN equivalent), **rocBLAS**/**hipBLASLt** (BLAS/GEMM, AMD's cuBLAS/cuBLASLt equivalents), and **Composable Kernel (CK)** as the shared, high-performance HIP C++ kernel backend underneath both. All three libraries now live in the unified `ROCm/rocm-libraries` monorepo under `projects/` and are served to frameworks via an emerging plugin layer called **hipDNN**, which dispatches to provider plugins (`miopen-provider`, `hipblaslt-provider`) using a graph-based engine model. MIOpen handles convolution, batch normalization, pooling, attention (through CK-tile FMHA pipelines), and kernel fusion. rocBLAS handles traditional BLAS (levels 1–3) with MFMA-aware tiled kernels generated by the **Tensile** code-generator. hipBLASLt extends rocBLAS with flexible epilogue fusion (bias, ReLU, GELU, SiLU/Swish), algorithm heuristics, and a cuBLASLt-compatible API, and is the default GEMM backend for PyTorch's `TunableOp` on Instinct hardware. The kernel dispatch chain — `hipBLASLt API → rocBLASLt backend → Tensile/rocRoller kernel selection → MFMA Matrix Core instruction` — closely parallels NVIDIA's `cuBLASLt → cuBLAS → Tensor Core` path, though AMD exposes more of the selection machinery through per-problem tuning files.

## Data Flow: GEMM Through rocBLAS → CK/Tensile → Matrix Cores

This traces a linear-layer forward pass in PyTorch on an MI300X.

1. **Framework dispatch**  
   PyTorch's `aten::mm` (or `aten::linear`) reaches the ROCm ATen backend. Since ROCm 2.2 (PyTorch 2.2+), `TunableOp` intercepts the call and selects the best backend — either `rocBLAS` or `hipBLASLt` — based on a per-problem benchmark cache.

2. **hipBLASLt API call**  
   `hipblasLtMatmul(handle, matmulDesc, alpha, A, Adesc, B, Bdesc, beta, C, Cdesc, D, Ddesc, &algo, workspace, stream)` is called. The `matmulDesc` encodes epilogue type (e.g., `HIPBLASLT_EPILOGUE_RELU`), transpose flags, and compute type.

3. **rocBLASLt backend selection** (`hipblaslt/library/src/amd_detail/rocblaslt/src/tensile_host.cpp`)  
   `tensile_host.cpp` is the sole file allowed to `#include` Tensile headers. It queries `Tensile::MasterSolutionLibrary` — a compiled-in solution database keyed on `{M, N, K, batch, dtype, transpose, arch}`. If `HIPBLASLT_USE_ROCROLLER` is set and the shape matches, `rocroller_host.cpp` is called instead for JIT generation via Origami tile selection + rocRoller compilation.

4. **Kernel selection by Tensile**  
   `MasterSolutionLibrary::findBestSolution(problem)` returns a ranked `HipSolutionAdapter` pointing to a pre-compiled `.co` code object. The solution was generated offline by Tensile's Python generator emitting MFMA assembly. For `gfx942` (MI300X), the typical tile is `MT128x128` with `mfma_f32_32x32x8_bf16` or `mfma_f32_16x16x16_bf16` instructions.

5. **MFMA execution**  
   The selected `.co` kernel launches on the CUs. Each wave32/64 executes MFMA instructions (`v_mfma_*`) which perform matrix-multiply-accumulate using the physical Matrix Cores on CDNA3. Inputs are loaded from LDS (shared memory) using vectorized `ds_read_b128` instructions; results accumulate in VGPRs.

6. **Epilogue**  
   If a fused epilogue was requested (bias, ReLU, GELU, Swish), the Tensile-generated kernel applies it in the same pass before writing D back to HBM, avoiding a separate kernel launch.

### MIOpen Convolution Data Flow (brief)

1. `miopenFindConvolutionForwardAlgorithm()` runs benchmark or database lookup → selects algorithm (GEMM, Winograd, FFT, Direct).
2. If GEMM: delegates to rocBLAS/hipBLASLt via `im2col` + GEMM.
3. If Winograd/Direct: dispatches to a CK or MIOpen-internal kernel.
4. **Fusion path**: `miopenFusionPlanCompile()` lowers a fusion graph (e.g., Conv→BatchNorm→ReLU) to a single CK or OpenCL kernel, eliminating intermediate HBM round-trips.

## Hardware Interface

| HW Feature | Software Hook | Notes |
|---|---|---|
| **Matrix Cores (MFMA)** | Tensile-generated `.co` kernels; CK `BlockGemmXdlops` warp tile | CDNA2 (gfx90a): 4096 FLOP/cycle per CU at BF16; CDNA3 (gfx942): doubled with FP8 support |
| **HBM bandwidth** | Tensile `prefetch_global_read`, CK-tile async pipeline stages | Async DMA loads overlap with MFMA execution |
| **LDS (shared memory)** | CK block-tile `ds_read/write`; Tensile `LdsPad` tuning | Padding avoids bank conflicts; MI300X: 64 KB LDS/CU |
| **FP8 / MX datatypes** | hipBLASLt `hipDataType_t` FP8 variants; CK `fp8_t`; `mxdatagenerator` | gfx942 native FP8 Matrix Core instructions |
| **Structured Sparsity (2:4)** | `hipsparselt`; CK-tile `FP16 2:4 structured sparsity` in universal GEMM | Hardware-accelerated via sparse Matrix Cores |
| **Stream-K** | CK-tile Stream-K GEMM; rocRoller StreamK grid | Work-stealing decomposition for better load balance on small M |
| **ROCr / HIP Runtime** | `hipLaunchKernel`, `hipModuleLoadData` for `.co` loading | All kernel dispatch goes through HIP; rocBLAS manages kernel `.co` lifetime |

## Key Findings

1. **CK is the shared kernel foundation.** Both MIOpen (for direct-algorithm conv, attention, and fusion paths) and hipBLASLt (for GEMM) ultimately rely on Composable Kernel primitives. CK-tile (`include/ck_tile/`) is the actively developed next-generation variant with a cleaner per-op single-header include model.

2. **hipBLASLt is the preferred GEMM backend over rocBLAS directly.** For `gfx12` architectures (RDNA4), hipBLASLt is set as the default; it falls back to Tensile for shapes not covered by its solution database. PyTorch's `TunableOp` benchmarks both backends at first use and caches the winner.

3. **Two competing JIT backends: Tensile (incumbent) vs rocRoller (emerging).** Tensile is Python-based offline code-generation producing pre-compiled `.co` files; rocRoller is a C++ JIT compiler selected at runtime via `HIPBLASLT_USE_ROCROLLER`. rocRoller uses Origami (tile size predictor) and a `SolutionCache` for reuse. This dual-backend design parallels NVIDIA's cuBLAS offline + TensorRT JIT model.

4. **MIOpen Fusion API enables operator fusion** comparable to cuDNN's fusion engine. A `miopenFusionPlan_t` encodes a DAG of operators (convolution, bias, batchnorm, activation) and compiles them to a single kernel. Primary consumers are TensorFlow/XLA and PyTorch.

5. **hipDNN provider plugin architecture is new and under active development.** The `dnn-providers/` layer (`miopen-provider`, `hipblaslt-provider`) wraps MIOpen and hipBLASLt as interchangeable engine plugins behind a common `hipDNN` graph-based API — analogous to cuDNN's backend API introduced in cuDNN 8. The hipblaslt-provider README explicitly marks the project as under active construction.

6. **CK-tile FMHA implements Flash Attention with async pipelines.** `block_fmha_batch_prefill_pipeline_qr_ks_vs_async.hpp` shows a full async-load prefill pipeline for multi-head attention (with batch, causal masking, KV-cache variants, rotary embeddings, paged attention). This is AMD's native alternative to FlashAttention-2/3 and avoids dependence on Triton.

7. **Performance gap with NVIDIA is narrowing but present.** GEMM tuning on MI300X with hipBLASLt has achieved up to 7.2× throughput improvement over baseline for LLaMA/Mistral workloads (Nscale 2025). However, the ecosystem matures slower: cuDNN covers more ops out-of-the-box, while MIOpen documents that Transform-Tensor, Dropout, and RNNs are not yet supported.

8. **gfx942 (MI300X) is the primary optimization target.** Tensile solution libraries, CK tile configs, and FP8 Matrix Core paths are all specifically tuned for `gfx942`. The `mfma_16x16` tile size generally outperforms `mfma_32x32` for large GEMM on MI300X due to better register pressure balance.

## Relation to Hardware Architecture

The MIOpen/rocBLAS/hipBLASLt stack is designed around AMD's CDNA architecture compute model:

- **CU-level tiling**: CK's `BlockGemmXdlops` maps the MxNxK GEMM tile to a single CU, with wave-level MFMA instructions consuming the innermost Kx-tiles. The four-level hierarchy (grid → block → warp → thread) in CK directly maps to `gridDim → workgroup → wavefront → lane`.
- **CDNA3 Matrix Cores**: The `v_mfma_f32_32x32x8_bf16_1k` instruction computes a 32×32×8 matrix multiply in one instruction. Tensile emits sequences of these with double-buffered LDS to keep the matrix cores fed.
- **HBM3 bandwidth (MI300X: 5.3 TB/s)**: The async prefetch pipelines in CK-tile (`*_async` pipeline variants) overlap HBM→LDS DMA with MFMA execution, targeting >80% bandwidth utilization for bandwidth-bound GEMMs.
- **Unified Memory (MI300X)**: The MI300X's CPU+GPU unified HBM means rocBLAS/MIOpen can operate on CPU-allocated tensors without explicit `hipMemcpy`; PyTorch's unified memory allocator takes advantage of this.
- **FP8 and MX support**: `mxdatagenerator` (in `shared/`) generates microscaling (MX) format test data; hipBLASLt and CK-tile both have FP8 GEMM paths targeting the CDNA3 native FP8 Matrix Core instructions available on gfx942/gfx950.
