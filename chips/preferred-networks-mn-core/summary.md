# Preferred Networks MN-Core — Software and Hardware Stack Summary

*as_of: 2026-09-13*
*chip: preferred-networks-mn-core*
*device_class: Compiler-Scheduled SIMD Accelerator (Japan)*
*Representative products: MN-Core 2 (shipping, TSMC N7); MN-Core gen 1 (superseded, TSMC 12 nm); MN-Core L1100 / L1400 (pre-silicon, 2027 target)*

---

## Overview

**Preferred Networks, Inc. (PFN)** — Tokyo, founded 2014 as a deep-learning company (the original authors of Chainer) — designs the **MN-Core** family of accelerators in collaboration with **Kobe University** (Prof. Junichiro Makino's group; Makino is also PFN's CTO of Computer Architecture). Development began in 2016.

MN-Core belongs in a survey about *software stacks* because of what its hardware **omits**. PFN's own framing, repeated verbatim across the whitepaper, the business page and every recent press release: functions "such as network control circuits, cache controllers and command schedulers, are incorporated in the compiler software rather than the hardware." The Software Developer Manual is blunter — "There are no hardware-managed caches in MNCore 2, and all the intra-board data transfers are explicitly managed by using machine code instructions. Instructions are sent to the board in a single stream and there are no mechanisms to manage the control flow of the execution." And the whitepaper: "Processing Element (PE) on the accelerator does not have its own program counter or instruction decoder. All PEs operate in perfect synchronization, receiving instruction sequences generated by the host CPU directly from the host."

Note the precise consequence: this is **not** merely "scheduling moved into the compiler". The host CPU is part of the *run-time* execution model, streaming a single instruction stream over PCIe to a device that cannot fetch instructions for itself. PFN quantifies the payoff at **7.4 % of transistors in arithmetic units**, against its own anonymized measurements of 1.7 % for "GPU N" and 2.4 % for "Accelerator P" (vendor claim, PFN's own research).

Three generations are public:

- **MN-Core** (gen 1, TSMC 12 nm, 4 dies/package) — **deployed in production**: it powered the **MN-3** supercomputer (three Green500 #1 finishes, one independently verified by TOP500) and the commercially sold **Matlantis** materials-simulation service. Superseded.
- **MN-Core 2** (gen 2, TSMC N7, single 550 mm² die) — the current part. **Shipping as complete Japanese-market systems** with published list prices (MN-Server 2 ¥20 M, Devkit ¥2 M) since ~September 2024, plus the PFCP cloud service. ~256 boards confirmed in PFN/NEDO testbeds. No merchant bare-chip sales, no non-Japanese customers, no third-party OEM.
- **MN-Core L1100 / L1400** (the "MN-Core L1000" architecture, DRAM-on-logic 3D stacking) — **announced, pre-silicon, mockup only, 2027 target**. Do not describe as shipping.

Internally MN-Core 2 is **GPFN3**: the management tool is `gpfn3-smi`, the emulator `gpfn3_package_main`, the assembler `assemble3`, and the MLSDK docs state verbatim that these target "MN-Core 2 (also known as GPFN3)".

## Software Stack

```
PyTorch (PFN custom torch build; the ONE supported framework)
  → fx2onnx (torch.fx + FakeTensor)            → Exported ONNX
  → PFVM Compiler (also a LibTorch runtime)    → Compiled ONNX
  → codegen Graph Compiler (historic "L3IR")   → MNGraph  [Dtype / Location / Layout]
  → codegen Code Emitter (Concat / L1Merge)    → GPFNApp  (FlatBuffers-packed VSM + relocations)
  → codegen runtime → libgpfn3 → gpfn3.ko → MN-Core 2 board
```

**Openness in one sentence:** everything load-bearing — PFVM, codegen, the runtime, the operator library, the assembler, the emulator, the user-space driver and the kernel module — ships as **binary `.deb` packages** from a private Google Artifact Registry APT repo under an EULA; `github.com/pfnet/mncore` is Apache-2.0 but contains only Dockerfiles, apt scripts and examples. SDK v0.5's release note "SDK source now public" is misleading in exactly that way.

**And yet the documentation is exceptional.** A complete ~130-page ISA manual, a free (no-login) assembler and cycle-faithful emulator, an educational from-scratch graph compiler on GitHub, and a public assembly-optimization contest. That combination makes MN-Core the most *reproducible* proprietary stack in this registry despite being closed.

### Framework integration

There is no eager device. You isolate a **pure function** `Callable[[Dict[str, Tensor]], Dict[str, Tensor]]`, register parameters and buffers with a `Context`, and compile it — with **forward, backward and the optimizer step all fused into a single device program**, because there is no host-side per-op control flow and no device-side branching. Device-side fused optimizers (`MNCoreSGD` / `MNCoreAdam` / `MNCoreAdamW`) are compiled into the same program; PFN warns `MNCoreAdamW` is not bit-compatible with LibTorch.

Portability is a device string over identical source: `pfvm:cpu` → `pfvm:cuda` → `emu2` → `mncore2:auto`. PFN recommends validating on `pfvm:*` first, because the PFVM graph rewrite is the hardest stage to debug — the (PyTorch graph vs Compiled graph) × (LibTorch vs codegen kernels) matrix gives four checkable combinations for bisecting a numerical regression.

Coverage evidence: a published HuggingFace `timm` survey (SDK v0.4) reports **378 compilable, 369 inference-ready, 156 training-ready** backbones. Static shapes only. LLM inference is labelled **experimental**; there is no vLLM, no TensorRT-LLM analogue, no ONNX Runtime EP. JAX is claimed on PFN marketing pages but appears nowhere in the SDK documentation — treat as unsubstantiated.

### The compiler — where the architecture actually lives

Every `MNValue` in MNGraph carries three compiler-assigned properties, and this trio *is* the MN-Core programming model:

1. **Dtype** — mixed precision managed graph-wide (GEMM/conv demoted to Half, BatchNorm restored).
2. **Location** — **DRAM or LM0/LM1 only.** GRF and L1BM/L2BM are never Locations; those tiers are scratchpads inside operator implementations.
3. **Layout** — how the tensor maps across the physical memory *tree*, in a notation like `(64,128)/((8_L2B:1, 8:2), (16_MAB:1, 2:1, 4_PE:1); B@[L1B,W])` over levels `{PE, W, Addr, MAB, L1B, L2B, Time}`.

The documented pass order is Dtype Planner → Location Planner (initial) → **Layout Planner** (inserts `MNCoreLayoutSwitch`; variant `lpz` recommended) → Location Planner (inserts `MNCoreUpload`/`MNCoreDownload`) → **Time-Slice** (adds a `Time` subaxis when a value exceeds the 2048 LW LM capacity) → Location Planner (sliced) → **Node Simulation** (actually compiles each node under multiple configurations to *measure* cycle counts) → **Scheduler** (spill/refill, LM0↔LM1 moves, `Forget`, and **rematerialization** via `auto_recompute_sa` simulated annealing) → Address Planner → Gene propagation.

So the compiler performs *cache replacement*, *physical-topology data placement*, *capacity management*, *rematerialization* and *instruction packing* — decisions a GPU hands to hardware. Presets run `O0` → `O4`; there are ~35 documented `CODEGEN_*` environment variables, including **`CODEGEN_AUTO_RECOMPUTE_HACK_FOR_QWEN`**, a candid signal of how much per-model rescue the "compiler handles it" promise still needs.

### Runtime and low-level programming

The deployable artifact is **GPFNApp**, a FlatBuffers container holding the assembled VSM, I/O metadata (name, Dtype, Layout, Address), model parameters, and relocation info. The runtime is explicitly designed around GPFNApp *reuse* — "particularly suitable for workloads that repeatedly execute the same computations" — with the stated corollary that "it performs poorly with operations requiring extensive indexing". All host↔device traffic funnels through **Group 0's PDM** over PCIe, with layout transposition done on the host CPU during upload.

Below the graph compiler, three entry points exist: **MN-Core 2 assembly (VSM)** with a fully public ISA manual and a free assembler + emulator; **HPCSDK / MNCL**, an OpenCL-like C/C++ environment that is **alpha with no public documentation** (OpenACC was promised in 2023 and is still undocumented in 2026); and `pfnet/mncore_simple_graph_compiler_for_education`, a publicly readable teaching compiler that takes an MLP from `torch.fx` to VSM and trains MNIST on the emulator (⚠️ **no LICENSE file** — not "open-source-licensed").

**Users cannot add operators.** `codegen/layers` is not shipped as source; PFN says the extension framework is "being prepared", with no timeline.

### Communication

**There is no collectives library** — no NCCL/RCCL/CNCL analogue and no device-side collectives. Multi-board and multi-node execution goes **through the host**: OpenMPI plus `torch.distributed` on the **`gloo`** backend with host-memory send/recv, as in PFN's own `run_pp_llama.py` pipeline-parallel example.

### Platform

Kernel module `gpfn3` (DKMS), user-space `libgpfn3`, and `gpfn3-smi` (the `nvidia-smi` analogue) install from the `mncore-packages` APT repo. Host OS support is **Ubuntu 24.04 / 22.04 only**, container-first. The cloud path is **PFCP**, a multi-tenant managed Kubernetes operated by **Preferred Computing Infrastructure** (PFN / Mitsubishi Corporation / IIJ JV), exposing MN-Core 2 as the extended resource `preferred.jp/mncore2`; pricing is not published.

**The public developer story is about six months old.** The SDK Hub (dev.mn-core.com) launched 2026-06-22; before 2026 the SDK was effectively PFCP-internal.

### Software Stack Update (2026-09-13)

**MN-Core SDK v0.8 released 2026-08-26** (dev.mn-core.com/news/en/) — the only SDK release in the 2026-08-08 → 2026-09-13 window (v0.7, 2026-07-15, was already on file). ## Hardware Architecture

### MN-Core 2

| Parameter | Value |
|---|---|
| Process / die | TSMC **N7**, **550 mm²**, single die, **22 B** transistors |
| Clock | **750 MHz** |
| PEs / MAUs | **4096 PEs**, **1024 MAUs** (derived: 4 PEs + 1 MAU = 1 MAB) |
| Peak FP64 / FP32 | **12 / 49 TFLOPS** |
| Peak pseudo-single ("TF32") / half ("TF16") | **98 / 393 TFLOPS** — PFN block-FP formats, *not* NVIDIA TF32 or IEEE binary16 |
| Power | **330 W (design value)** — measured TDP not disclosed |
| Efficiency | 37.24 (FP64) / 148.9 (FP32) / 297.9 (pseudo-single) / **1192 (half) GFLOPS/W** |
| On-chip SRAM | 128 MiB LM + 16 MiB GRF + 4 MiB L1BM + 2 MiB L2BM + 16 MiB PDM ≈ **166 MiB** *(our arithmetic — PFN publishes no aggregate)* |
| Off-chip memory | **16 GiB GDDR6, 512 GB/s** (4 GiB / ~128 GB/s per Group) |
| Host interface | **PCIe Gen5 ×16**; PCI vendor ID `0ccd` |
| Chip-to-chip fabric | **None** |

> ⚠️ **The famous 1192 GFLOPS/W is the half-precision figure only.** FP64 efficiency is 37.24 GFLOPS/W. Quoting 1192 without the precision qualifier is the single most common error about this chip.

### The tree

Top Level → 4 Groups → 8 L2Bs → 64 L1Bs → 1024 MABs → 4096 PEs. There is **no cache at any level and no NoC**: each tier is a broadcast/reduction network with a fixed repertoire of modes (broadcast, individual, reduction, distribute/collect), symmetric by design so that a `collect` reassembles exactly the layout a `distribute` produced. Makino's argument: broadcast and reduction "are the two most important communication patterns for PEs used for tensor operations in deep learning. Compared to shared cache, energy consumption becomes much smaller."

Only **Group 0's PDM** is physically wired to the host over PCIe, so *all* host I/O passes through one 4 MiB SRAM.

### Execution model

Two instruction classes: **MV** (movement among PDM/DRAM/L2BM, asynchronous) and **PE** (VLIW, controls everything at L2B and below). A **PE instruction covers 4 cycles — a "step" —** and the SDM's footnote is the key disclosure: *"This is because 1 cycle per instruction would saturate the PCIe bandwidth between the host and the board."* **The instruction issue rate is set by the host link, not by the silicon.** There are **no hazard interlocks** ("it is the programmer's responsibility"), **no branches** (mask-register predication only), an explicit `wait` field in every PE instruction for synchronization, and architecturally visible forwarding operands (`mauf`, `aluf`, `lbf`, `mreadf`, `nowrite`).

### Numerics — not IEEE-754

Half is **1-6-9**, not binary16's 1-5-10. **There are no denormals and no NaNs at all**: exponent all-zero is ±0 regardless of mantissa, all-ones is ±∞ regardless of mantissa. Matrix operands must be **block-floating-point** converted, and on MN-Core 2 BFP is used at *all* precisions including FP64 (gen 1 used it for half only). Assembly is untyped; storage is big-endian.

### Generation 1, for context

TSMC 12 nm, **4 dies × 764 mm²** per package, 2048 MABs (8192 PEs), 500 MHz, 32 GB LPDDR4 @ 400 GB/s, PCIe Gen3 ×16, ~500 W (estimated), 32.8 TF DP / 131 TF SP / 524 TF HP. Gen 1 *did* have a proprietary scale-up fabric — **MN-Core DirectConnect** with dedicated switches, 32 servers + 2 switches per "Zone". **No gen-2 equivalent is documented**, and PFN has never stated whether it was dropped or merely unused.

The **MN-3** supercomputer (gen-1 MN-Core) took Green500 #1 in June 2020 (21.11 GFLOPS/W), June 2021 (**29.70**, independently confirmed by TOP500) and November 2021 (**39.38**), plus #2 in November 2020 and #5 in June 2022. **No Green500 result exists for MN-Core 2.**

### Vendor-reported performance

PFN's own Hot Chips 36 measurements against A100 (*vendor claim, 2024-08-27*): ResNet-50 training 77 TF FP16 vs 33.2 TF BF16; ResNet-50 inference 154 vs 33.7 TF; **HIMENO 9.03 TF FP64 vs 0.634 TF** (~14×, and ~75 % of MN-Core 2's FP64 peak on a memory-bound stencil — the clearest evidence that 128 MiB of software-managed LM is doing real work). LLM inference on PLaMo-3-NICT-2B: 5,100 tok/s prefill, 11.8 tok/s decode. **No MLPerf or other third-party-audited results exist for MN-Core 2.**

## MN-Core L Series — Pre-Silicon

**MN-Core L1000 is the family/architecture name**; the SKUs announced 2026-06-01 are **MN-Core L1100** (low-power) and **MN-Core L1400** (high-performance), both targeting **2027** — a one-year slip from the 2026 target in the original 2024-11-15 announcement. A **mockup** was shown at SC25 (Nov 2025) and photographed in the June 2026 press release; PFN's roadmap marks the family 開発中 (in development).

The point of the part is memory: "PFN's proprietary **logic and DRAM are vertically stacked**, with many electrodes arranged across the surface." This is **DRAM-on-logic 3D stacking** — explicitly not HBM and not commodity DIMM DRAM. PFN claims **"50 times higher memory bandwidth than MN-Core 2"** (which would imply ~25.6 TB/s, *derived from a vendor claim, not a published spec*) and that "a single MN-Core L1400 card is designed to provide the memory bandwidth and memory capacity required for inference" of 70 B-parameter LLMs. The earlier 2024 claim was different in kind: "up to a ten-fold increase in computing speed compared with conventional processors such as GPUs."

**Process node, foundry, die size, memory capacity, absolute bandwidth, peak FLOPS, dtypes, TDP, form factor, price and interconnect are all not disclosed.** The Toyota Frontier Research Center engagement (2026-06-01) is **joint research on software** for an unreleased chip — not a deployment and not a customer win; robot tests happen only "following 2027 shipments."

**MN-Core L2000** (2028, "large-scale AI inference + HPC") appears **only** on PFN's roadmap graphic and in no press release. Treat as a roadmap tile.

Two unreconciled process statements exist for the generation after MN-Core 2: Makino's Hot Chips 36 slide says **"MN-Core Next for learning: >10× peak performance, >30× application performance, Samsung SF2"** (2024-08-27), while the PFN / **Rapidus** / SAKURA internet basic agreement (2025-01-08) says "Rapidus manufactures a new model of AI semiconductors in the MN-Core series to be designed by PFN". PFN has never publicly reconciled the two. **Report both as separate dated statements; do not merge them.** No "MN-Core 3" name has been found anywhere; re-checked 2026-09-13, still absent. No new Rapidus/PFN news found in the 2026-08-08 → 2026-09-13 window.

**Re-verified 2026-09-13, unchanged:** the PFN AI Chips business page still describes MN-Core L1000 as "under development" / prototype stage, and MN-Core 2 pricing is unchanged (MN-Server 2 ¥20M, Devkit ¥2M). No MN-Core L1100/L1400 availability date, spec disclosure, or silicon news found in the window.

## Deployment Scale

- **NEDO testbed, since July 2025**: direct-liquid-cooled MN-Core 2 servers (8 boards/node) — **30 nodes = 240 boards** at IIJ Matsue Data Center Park plus **2 nodes = 16 boards** at JAIST Ishikawa.
- **From April 2026**: moved into IIJ's Shiroi DCC modular liquid-cooled data center (**AImod**; design pPUE 1.1 free-cooling / 1.2 annual, WUE 0). Board count not disclosed.
- **PFCP cloud**: MN-Server 2 V1 nodes under multi-tenant Kubernetes; fleet size not disclosed, pricing not published.
- **Production applications, gen-1 MN-Core**: Matlantis (materials MLIP simulation, sold to ENEOS as a commercial cloud service since Aug 2023, ~3–5× vs GPU), PFN 3D Scan (~10×), Kachaka home-robot NAS (~7×). MN-Core 2 has been used in Matlantis only **experimentally**, via PFCP.

## Competitive Position

MN-Core is the cleanest published example of the "compiler owns everything" thesis, and its closest neighbour in this registry is **Groq's TSP** — but MN-Core goes further. Groq's compiler schedules a chip that still fetches its own instructions; MN-Core's PEs have **no program counter and no decoder at all**, and instruction supply is bounded by the host PCIe link by explicit design. Meta MTIA and Sophgo each retain a hardware-managed or partly hardware-managed memory path somewhere; MN-Core has none, at any tier, in any generation.

**Strengths.** Extraordinary FP64 efficiency for an AI-branded part (12 TFLOPS FP64 in 330 W, and ~75 % of that peak achieved on HIMENO) makes it a genuine HPC/AI dual-use chip, unlike most inference ASICs. The three-property MNValue model (Dtype / Location / Layout) is a reusable abstraction other compiler teams could adopt. Documentation openness — full public ISA, free emulator, teaching compiler, public contest — is better than almost any vendor in this survey.

**Limitations.** No chip-to-chip fabric and no collectives on MN-Core 2: multi-board goes through host gloo/MPI, which caps model-parallel scaling. 16 GiB at 512 GB/s is small and slow next to any HBM part, which is precisely what MN-Core L1000 is meant to fix. One framework, one custom torch build, static shapes only, no operator extensibility, LLM inference experimental. And the commercial footprint is small and domestic: complete systems at Japanese list prices, a Japanese cloud, ~256 confirmed boards, no merchant silicon and no non-Japanese customers.
